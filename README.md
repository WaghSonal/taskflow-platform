# TaskFlow Backend

A CQRS-over-EF-Core ASP.NET Core Web API backing the TaskFlow task management app — projects, tasks, users, departments, comments, attachments, time tracking, dashboards, and JWT-based authentication.

## Tech stack

| Concern | Choice |
|---|---|
| Runtime | .NET 10 |
| ORM | EF Core 10 (SQL Server) |
| CQRS dispatch | Hand-rolled `IRequest`/`IRequestHandler`/`Dispatcher` (see [`TaskFlow.Utility/Dispatcher.cs`](src/TaskFlow.Utility/Dispatcher.cs) — not MediatR, to avoid its commercial licensing on newer versions) |
| Auth | JWT bearer tokens (`Microsoft.AspNetCore.Authentication.JwtBearer`) |
| Password hashing | ASP.NET Core Identity's `PasswordHasher<T>` |
| Testing | xUnit + Moq + FluentAssertions + EF Core SQLite (in-memory) |

## Architecture

Seven projects, one dependency direction — nothing skips a layer, and controllers never touch a Command/Query handler directly:

```
TaskFlow.API            Controllers, JWT config, middleware, Program.cs
      ↓ calls into
TaskFlow.AppServices     One façade service per feature; owns Dispatcher.Send(...)
      ↓ dispatches
TaskFlow.Command / Query MediatR-shaped handlers — the actual write/read logic
      ↓ reads/writes through
TaskFlow.Infrastructure  EF Core: DbContext, entities, configurations, repositories
      ↓ shapes data with
TaskFlow.DTO / Utility   No dependencies of their own
```

```
src/
  TaskFlow.Utility/        Dispatcher, exceptions, shared constants — no project references
  TaskFlow.DTO/             Request/response records, one folder per feature
  TaskFlow.Infrastructure/  EF entities, DbContext, configurations, repositories
  TaskFlow.Query/            {Feature}/GetXQuery.cs + Handler
  TaskFlow.Command/           {Feature}/XCommand.cs + Handler
  TaskFlow.AppServices/         Contracts/IXService, Services/XService
  TaskFlow.API/                  controllers/, Middleware/, Program.cs
test/
  TaskFlow.UnitTest/
```

## ⚠️ Important: this API maps onto an existing, hand-authored database

`Users`, `Roles`, `Projects`, `Tasks`, `Departments`, and every other table already exist in **`TaskManagementDB`** — created by hand in SSMS (see `../Task Management Queries/*.sql` in the repo root), not generated by EF Core. Because of that:

- **No EF Core migrations are used or should be run** (`dotnet ef migrations add` / `database update`) against this database. EF's entity configurations (`src/TaskFlow.Infrastructure/configurations/`) map onto the schema exactly as it already exists — column names, keys, and FKs mirror the real SQL, not EF's usual conventions (e.g. `User.UserId` not `User.Id`, `CreatedDate` not `CreatedAt`).
- **Schema changes go through SQL scripts**, the same way the tables were created — update the corresponding entity/configuration class by hand afterward to match.

## Prerequisites

- .NET 10 SDK
- SQL Server (this project targets a local **SQL Server Express** instance — `.\SQLEXPRESS` — with `TaskManagementDB` already created and populated via the scripts in `../Task Management Queries/`)
- (Optional) `dotnet-ef` global tool — only needed if you extend this project with new EF-managed tables later: `dotnet tool install --global dotnet-ef`

## Configuration

`src/TaskFlow.API/appsettings.Development.json`:

```json
{
  "ConnectionStrings": {
    "TaskFlowDb": "Server=.\\SQLEXPRESS;Database=TaskManagementDB;Trusted_Connection=True;TrustServerCertificate=True;MultipleActiveResultSets=true"
  },
  "Jwt": {
    "Issuer": "TaskFlow",
    "Audience": "TaskFlow.Frontend",
    "Key": "replace-with-a-real-256-bit-development-secret",
    "ExpiryMinutes": 120
  }
}
```

Point `ConnectionStrings:TaskFlowDb` at your own SQL Server instance if it isn't `.\SQLEXPRESS`. Replace `Jwt:Key` with a real secret before deploying anywhere beyond local development — see the `.gitignore` note about using `dotnet user-secrets` or environment variables for real secrets instead of committing them.

CORS is currently locked to the Vite dev server origin (`http://localhost:5173`) in `Program.cs` — add your deployed frontend's origin there when you have one.

## Running

```bash
cd Backend
dotnet build TaskFlow.slnx
dotnet run --project src/TaskFlow.API
```

The API listens on `http://localhost:5295` (see `src/TaskFlow.API/Properties/launchSettings.json`). Try it via `src/TaskFlow.API/TaskFlow.API.http` or:

```bash
curl -X POST http://localhost:5295/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@taskflow.com","password":"demo1234"}'
```

## API overview

All endpoints except `POST /api/auth/login` require `Authorization: Bearer <token>`.

| Controller | Route | Notes |
|---|---|---|
| `AuthController` | `/api/auth` | `login`, `me` |
| `ProjectsController` | `/api/projects` | CRUD + `/members` |
| `TasksController` | `/api/tasks` | CRUD, `/status`, `/tags`, `/dependencies`, `/comments`, `/attachments`, plus `statuses`/`priorities`/`tags` lookups |
| `UsersController` | `/api/users` | CRUD, `/active`, `/roles`, `/roles` lookup — Admin only |
| `DepartmentsController` | `/api/departments` | CRUD — Admin only |
| `TimeEntriesController` | `/api/time-entries` | Log/list/delete — logging time rolls up into the parent task's `ActualHours` |
| `DashboardController` | `/api/dashboard/summary` | Role-shaped summary (Admin/PM/Employee each see different fields) |
| `TeamController` | `/api/team/workload` | Project Manager/Admin only |

## Testing

```bash
dotnet test test/TaskFlow.UnitTest/TaskFlow.UnitTest.csproj
```

Runs against an in-memory SQLite database and mocked repositories — never touches the real `TaskManagementDB`.

## Known gaps

- No FluentValidation/pipeline validation layer yet — handlers do minimal inline checks.
- Attachments store metadata only; there's no real file upload/storage.
- A handful of fields the frontend's mock data assumed (`Project.progress`, `Department.managerId`) have no backing column in the real schema.
